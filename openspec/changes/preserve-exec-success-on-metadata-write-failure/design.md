# Design

## Context

Мотивация и согласованное внешнее поведение описаны в
[proposal.md](proposal.md#why) и
[delta spec](specs/exec-result-reporting/spec.md). Дизайн нужен, поскольку
изменение проходит через CLI и рендерер и должно сохранить защиту файлов.

### Подтверждённые факты

- В `b6ff33a` [execCommand](../../../internal/cli/cli.go) вызывает
  `Renderer.Success` только после `runner.Run` с `exitCode == 0` и `err == nil`.
  Сигналы и ненулевые коды уже проходят через `CommandFailed`.
- [Success](../../../internal/output/output.go) возвращает ошибку файла до
  вывода success envelope. `runStatus` преобразует обычную ошибку в
  `RUNTIME_ERROR`, код `1`, и вызывает error renderer. `CommandFailed` уже
  сохраняет child status и сообщает об отказе файла только с `--verbose`.
- `writeOutputFile` вызывает `ValidateOutputPath`, затем атомарную публикацию.
  [Предварительная проверка](../../../internal/cli/preflight.go) и повторный
  guard защищают конфигурацию и её lock-файл, включая файловые алиасы.
- Текущий human-вывод реального успешного `exec` молчит. JSON/JSONL печатаются
  даже с `--quiet`; успешные данные не содержат добавленного `exit_code: 0`.

Безопасное воспроизведение 2026-10-04 на macOS arm64, Go `1.26.8`: сборка
`go build -o <temporary-binary> ./cmd/env-vault`; запуск из временного каталога,
все три gate test backend заданы, путь store абсолютный под system temp,
mappings отсутствуют. Child — `/bin/sh -c 'printf child-completed; exit N'`,
аргументы CLI — `--quiet --output <temporary-directory> exec -- …`.

| N | Код env-vault | stdout | stderr |
|---|---|---|---|
| 0 | 1 | публичный маркер child | `RUNTIME_ERROR` и стандартная remediation |
| 7 | 7 | тот же публичный маркер | пусто |

Оба запуска не создали test store. Значения секретов не требовались.
`GOTOOLCHAIN=go1.26.8 go test ./internal/cli ./internal/output ./internal/runner`
прошёл на macOS с `GOCACHE` в system temp. Это baseline до реализации,
а не доказательство будущего поведения; Linux/Windows этим не проверены.

## Goals / Non-Goals

**Goals:**

- Отделить отказ файла от отказа stdout, сохранив общий формат успешного вывода.
- Локализовать будущий фикс в `internal/output` и успешной ветке `internal/cli`.
- Проверить границы через наблюдаемые статусы, потоки и сохранность файлов.

**Non-Goals:**

- Перестройка runner, атомарной записи и схем данных; новые флаги или error codes.
- Общий режим игнорирования ошибок `Success` или изменение broken-pipe semantics.
- Изменения Keychain, release-процесса и реализация продукта на этапе подготовки.

## Decisions

### Отдельный путь успешного реального exec

Добавить в `internal/output` метод
`Renderer.CommandSucceeded(command string, data any, warnings []string) error`.
Он строит прежний success envelope, один раз вызывает `writeOutputFile`, при
отказе пишет `OUTPUT_WRITE_FAILED: …` только с `Verbose`, затем продолжает
успешный вывод в терминальные потоки. Ошибка этого вывода возвращается вызывающему
коду, как прежде. Ошибка самой verbose-диагностики не меняет child status,
как и у существующего `CommandFailed`.

Общую часть после записи файла вынести в закрытый метод `writeSuccess`:
JSON/JSONL имеют приоритет над Quiet, затем human-вывод. Обычный `Success`
сохраняет немедленный возврат ошибки файла; менять его публичный контракт нельзя.
Только последний вызов `Success` для реального успешного `exec` заменить на
`CommandSucceeded`. Ветка dry-run и обработка runner errors остаются прежними.

Альтернативы: подавление всех ошибок `Success` скрывает ошибки stdout;
изменение общего `Success` затрагивает другие команды. Возврат `1` после успеха
child отвергнут владельцем из-за риска повторения уже выполненного действия.

### Одна публикация без изменения механизма записи

Не вызывать error renderer и не повторять child из-за отказа `--output`.
«Одна публикация» означает один вызов существующего `writeOutputFile` новым
success renderer: внутренние ограниченные повторы atomicfile на Windows
сохраняются. Если отдельно отказал stdout, остаётся нынешний путь `runStatus`
с `RUNTIME_ERROR`, который может попытаться записать error envelope; это другой
класс ошибки и не входит в нефатальную обработку файла.

Использовать существующие guard и atomicfile без обходов. Проверка перед
публикацией выполняется и после завершения child: обнаруженный новый алиас
отказывает в записи, но не отменяет уже состоявшееся выполнение.

### Регрессии на правильной границе

- Renderer: матрица human/JSON/JSONL, quiet/verbose, доступный/недоступный файл;
  счётчик guard подтверждает единственный вход в публикацию. Сохранять точный
  envelope без нового warning, error или `exit_code: 0`.
- CLI: отдельный файл без Unix build tag и child на основе тестового executable
  `os.Args[0]`. Проверять публичные маркеры, число запусков, коды `0`/`7` и
  диагностику; не зависеть от `sh` для переносимых сценариев.
- После предварительной проверки child создаёт hard-link между временной
  конфигурацией и metadata path. Проверять сохранение содержимого и того же
  файлового алиаса, код `0`, диагностику только с verbose. Для файловой системы
  без hard links отмечать явный skip; он не подтверждает этот сценарий.
- Для отказа stdout child должен молчать: writer возвращает ошибку при записи
  JSON/JSONL envelope, чтобы не спутать её с ошибкой копирования потоков runner.
- Unix-сигналы проверять существующим способом в
  [exec_output_test.go](../../../internal/cli/exec_output_test.go), дополнительно
  с недоступным файлом. Переносимый E2E расширить в
  [OUTPUT_JSON_JSONL_FILE](../../../e2e/scenarios_test.go), используя helper
  `streams` и существующую изоляцию тестового backend.

### Документация и совместимость

Обновить разделы вывода в README и основном design одновременно с будущим
фиксом: `--output` не влияет на успешный child status, старая запись может
остаться, verbose сообщает отказ, JSON/JSONL и строгие ошибки других команд
сохраняются. Миграция данных не нужна. Автоматизация, полагавшаяся на прежний
код `1` именно при отказе post-exec metadata, увидит намеренное изменение на `0`.

## Risks / Trade-offs

- Отказ файла может оставить устаревшие метаданные → описать это ограничение;
  не удалять прежний файл и не повторять child ради обновления метаданных.
- Случайное подавление stdout или runner errors → отдельные отрицательные тесты
  и точное условие входа `exitCode == 0 && err == nil`.
- Ослабление защиты при повторной проверке пути → CLI-тест с появившимся алиасом;
  общий guard и atomicfile не менять.
- Локальные тесты не доказывают native Linux/Windows → будущий прогон существующей
  CI-матрицы; отсутствие/skip проверок явно указывать в отчёте.
- Общий `go test ./...` может пропустить E2E без `ENV_VAULT_E2E_BINARY` → отдельный
  целевой прогон с собранным бинарником в [tasks.md](tasks.md).

**Предположения.** Достаточно существующих механизма записи и тестовых helper;
новые зависимости и ADR для локального исправления не нужны. Эти технические
допущения проверяются тестами, а не доступом к production backend.

**Вопросы.** Не осталось решений, требующих выбора владельца. Следующая граница —
review этих артефактов и отдельный запрос на реализацию.
