# Release-pipeline trim — execution plan (2026-07-30)

Owner decision (2026-07-30, after reviewing
`docs/pipeline-complexity-proposal-2026-07-30.md`): proceed with **trim**,
in this repo, as the priority track. This document sequences the cut.
Supersedes `docs/refactor-plan-v2.md`'s Track B framing (which assumed
existing release machinery stayed as-is) — Track A (product code:
`internal/errors`, `redact`, `output`, `secretstore`, `config`, `cli`) is
unaffected and still proceeds independently, in parallel or interleaved.

**Execution order changed (2026-07-30):** Phase 3 was executed before Phase 2.
Every consumer of the versioned contract's historical-authority surface
(`LoadHistoricalEvidence`, `LoadHistoricalBundleContract`,
`ValidateHistoricalBundleReconstruction`, `ValidateHistoricalEvidenceIdentity`,
and every `releasecheck evidence` subcommand) existed only to serve the
evidence ledger, and
`release-evidence.yml` was the single heaviest contract consumer at 988 lines.
Doing Phase 2 first would have meant rewiring ~9 files that Phase 3 then
deleted. Phase 3 has no reverse dependency on Phase 2, so the swap is a strict
improvement; the phase contents are unchanged.

Each phase is its own reviewed PR (AGENTS.md already requires this for any
release-related change), verified end-to-end (`brew install`/`upgrade`
still works) before the next phase starts. Per-phase status is recorded in the
phase headings below.

## Phase 0 — Safety net (no deletions) — **done (2026-07-30)**

- Confirm the current release (`v0.1.0`) is fully published, evidenced, and
  Homebrew-verified before cutting anything — do not trim mid-release.
- Tag the pre-trim state explicitly (e.g. `pre-trim-2026-07-30`) so the full
  removed machinery stays trivially recoverable from git history even after
  deletion, independent of GitHub's own history retention.

## Phase 1 — Drop GitHub Apps — **done (2026-07-30, PR #70)**

- Remove `env-vault-release-planning` and `env-vault-tap-release` App
  installations, their audit workflows (`audit-release-app.yml`,
  `audit-release-planning-app.yml`), and the key-rotation runbook section
  in `docs/release-operator-runbook.md`.
- Same-repo release steps revert to the default `GITHUB_TOKEN`.
- Cross-repo write (bumping `homebrew-tap`'s formula) needs *something* —
  simplest: one PAT scoped only to `homebrew-tap`, stored as a repo secret
  (or, fittingly, via `env-vault` itself once it has a real PersonalOS
  consumer — not required to unblock this phase). No App install/rotation
  lifecycle either way.

## Phase 2 — Drop the versioned release contract — **done (2026-07-30)**

- Remove `release/contract.v1.json`, `release/contract.v2.json`,
  `release/contract-history.v2.json`, and the historical-authority registry
  logic in `internal/releasecontract`, `cmd/releasecheck contract ...`.
- The workflow YAML becomes the single source of truth for release
  identities (App slugs are gone anyway after Phase 1; remaining identity
  checks — target repo, branch, tag pattern — are plain workflow
  conditionals, same as `macos-user-settings/release.yml`).
- Remove ADR 0006 from "active design" status — mark it superseded by this
  plan, keep the file for history (ADRs are not deleted, per this repo's
  own convention of never rewriting decision history).

**As executed, with one deliberate deviation.** Everything *versioned* is gone:
`release/contract.v1.json`, `release/history/contract.v1.json`,
`release/contract-history.v2.json`, `internal/releasecontract/{history,route}.go`,
the `contract route-source`/`historical-source` commands and their schemas, the
`evolution` predecessor pin, the `apps` registry type, and every dual-generation
branch in the validator. The three workflows that routed a v1 source now read
`release/contract.v2.json` — from the checkout for planning, from the exact
immutable source commit for the two repair workflows — and require the source
and the reviewed control plane to agree on naming, platforms, assets, the
promotion-manifest schema, and workflow identities.

**The deviation:** `release/contract.v2.json` itself is kept, rather than
deleted in favour of "workflow YAML as the single source of truth". Deleting it
would not remove machinery, it would *duplicate* data: the five-platform matrix
is generated from it (`releasecheck contract matrix`), and `releasepromotion`,
`releasearchive`, `e2ebaseline`, `releasesettings`, and `actionsartifact` all
consume it as typed config. Hardcoding those platforms and ten asset names into
both YAML and Go is more surface, not less. What made the contract expensive was
the *versioning* around it, and that is what this phase removed. The file name
and schema id keep the `v2` suffix: renaming them would churn ~55 references and
the frozen capability fixtures for no behavioural gain.

## Phase 3 — Drop the evidence ledger — **done (2026-07-30)**

- Remove `internal/releaseevidence`, the `release-evidence` branch/workflow
  (`release-evidence.yml`), genesis/legacy routing, and the bounded
  64-commit window entirely — this also retires backlog item 11 (the
  checkpoint/Merkle design) as moot; nothing to design if the ledger itself
  is gone.
- The GitHub Releases page plus ordinary git/PR history becomes the audit
  trail — matches every other repo in the account.

**As executed.** `internal/releaseevidence`, `release-evidence.yml`, the
`releasecheck evidence` subcommands, the four evidence publishing scripts, and
the ledger-only parts of `internal/releasecontract/history.go` are gone; the
publisher's `health` job keeps every live verification but no longer seals or
uploads an observation. Deliberately left for Phase 2 (they serve the versioned
contract, not the ledger): `RouteSourceContract`/`AuthorizeHistoricalSource`,
`release/contract-history.v2.json`, and the `evidence_format` field in the
route document, which is frozen identity for the v1 generations. The
`release-evidence` branch, its protective ruleset, and the durable replay
artifacts already in Actions storage stay untouched as frozen history; the
artifact-lifecycle policy keeps their name patterns so the cleanup tooling can
still classify them.

## Phase 4 — Drop dual-source historical-tag verification — **done (2026-07-31)**

**As executed, in the same PR as Phase 5** (the phase has zero code surface, a

## Phase 5 — Drop the current provenance/SBOM generation — **done (2026-07-31)**

- Remove the current bespoke provenance/SBOM code entirely (no replacement
  in this phase). The properly-scoped replacement is deferred: see
  `docs/release-refactor-backlog.md` item 14 (added alongside this plan) —
  built later, on a different (isolated-builder) architecture, only if a
  real consumer or security need appears. Do not carry old code forward
  "just in case."

**As executed.** The publisher's `supply_chain` job is deleted whole (it
existed only for attestations), along with the SBOM extractor
`cmd/release-extract`, `artifact-attestation-state.sh`,
`verify-artifact-attestations.sh`, the homebrew job's attestation gate, the
health job's ten `gh attestation verify` re-checks, every `attestations:`
permission, the `supply_chain` contract stage (ordinals renumbered) and
publisher-job entry, and the bridge's attestation gate and
`supply_chain_job_id` input. The `spdx-sbom` upload site left the artifact
policy but its name pattern stays, so the SBOM artifacts already in Actions
storage remain classifiable (same treatment as the Phase 3 evidence
patterns). Existing v0.1.0 attestations on GitHub's registry are untouched —
they are immutable history, they just stop being regenerated or re-verified.
The repair bridge's failed-publisher shape check was still pinned to the
pre-Phase-1 App-era job graph (a latent Phase 1 leftover — it could only ever
match the historical v0.0.16 incident); it is re-pinned to the current
six-job graph with an explicit "exactly one failed step, every tap-mutation
step skipped" invariant.

## Phase 6 — Simplify the release-confirmation ceremony — **done (2026-07-30)**

- Replace the byte-exact `ПОДТВЕРЖДАЮ RELEASE …` tuple and the resumable
  authorize-and-merge wrapper with one explicit, human-readable "yes,
  publish" confirmation step (still deliberate, still requires the owner's
  explicit action — just without the exact-tuple/no-paraphrase machinery
  calibrated for a confirmer who might not be the PR author).

**As executed, and executed early.** The owner instructed on 2026-07-30 to drop
the exact-prompt rule outright, so this phase ran before Phases 4/5 and went one
step further than planned: there is no separate confirmation step at all.
**Merging the generated release pull request is the authorization**, and it must
be head-guarded (`gh pr merge <n> --squash --match-head-commit <head-sha>`), so a
head that moved during review still cannot be published silently.
`scripts/release/authorize-and-merge-release-pr.sh` and its 697-line operator
test are deleted; `verify-release-authorization.sh` keeps every identity check
(exactly one generated release PR with the contract's title/header/footer/label/
base merged to that exact source commit, agreeing manifest version at source and
at `main`, typed successful `main` CI attempt) and only lost the
confirmation-comment block. The Actions-artifact-deletion ceremony
(`ПОДТВЕРЖДАЮ DELETE ACTIONS ARTIFACTS …`, ADR 0007) is deliberately kept: that
operation is irreversible and has no release gate behind it.

## Phase 7 — `cmd/*` and `internal/*` cleanup — **done (2026-07-31)**

- Delete now-dead binaries/packages once Phases 1-6 land:
  `cmd/releasecheck` subcommands tied to the removed contract/evidence
  systems, `cmd/releasetransport`/`internal/githubtransport` if the
  remaining `gh api` surface is small enough for inline calls (re-evaluate
  against `macos-user-settings`'s inline-`gh` pattern — do not assume,
  measure the remaining call count first), `internal/actionsartifact*` if
  the artifact count naturally drops enough that the lifecycle-policy
  tooling is no longer needed (re-check via `gh api
  repos/.../actions/artifacts` before deciding, per the existing
  `docs/actions-activity-report-2026-07-30.md` baseline of 373).

**As executed, measured first.** Removed: `releasecheck metrics`/`metrics
compare`, `internal/releasemetrics`, `release/metrics-baseline.v1.json`, the
three metrics schemas from the contract and checker capability list, and the
metrics halves of runbook card 14 and RELEASING.md — zero automation callers,
and the checked-in baselines described the pre-trim 25-job CI / 30-job
publisher, so every comparison against them was meaningless after the trim.
Kept, against the plan's own criteria: `cmd/releasetransport` +
`internal/githubtransport` (measured 16 typed `actions identity` call sites
plus reads across live workflows — the surface is not small);
`internal/actionsartifact*` + `cmd/actionsartifact*` (artifact count measured
2026-07-31 at **859**, up from the 373 baseline — the lifecycle tooling is
more relevant, not less; backlog item 13 still awaits owner review); every
other `releasecheck` subcommand (live workflow/script/runbook callers:
validate-contract 10, contract operational 8, promotion 8, classify-attempt 6,
settings 3, matrix 3, legacy 1, recovery in operator cards);
`internal/releasearchive` (e2e-runner) and `canonicalgzip`/`strictjson`
(actionsartifact, transport).

## Phase 8 — Verify end-to-end

- Cut one real release through the trimmed pipeline. Confirm: binaries
  build for all 5 targets, GitHub Release is created, Homebrew formula
  updates, `brew upgrade env-vault` works on at least one real machine.
  This is the actual acceptance test for the whole trim — not any internal
  metric.

## What does not change

- Native 5-platform build matrix, checksums, E2E suite on real platforms,
  Homebrew distribution itself, and Track A (product code) are untouched
  by this plan.
