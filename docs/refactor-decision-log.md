## Вопрос 1: P0-пункты backlog.md выглядят выполненными, но не закрыты — включая ревокацию токена

**Где:** `backlog.md:5-10` (раздел P0)

**Что противоречит чему:**
`backlog.md` держит в P0 (наивысший приоритет, без даты, без статуса):
- «Verify public GitHub repository settings after first push.»
- «Revoke the one-time GitHub token used for initial publication.»
- «Confirm no secret values in logs with regression test.»

Это бутстрап-эпохи пункты (ADR 0000, до появления GitHub Apps). Но
`docs/design.md:270-283` описывает уже работающий, регулярно запускаемый
`audit-release-planning-app.yml`, который «adds Administration read to prove
repository settings, branch/tag ruleset structure, actor-independent GraphQL
zero-bypass counts» — то есть настройки репозитория уже проверяются
автоматически и не одноразовым ручным шагом. А `docs/design.md:199-204`
описывает «a clean sentinel leak scan» как часть fail-closed E2E gate —
похоже на уже реализованную регрессионную проверку утечки секретов в логах.
Проект уже выпустил минимум `v0.0.17` (`release-refactor-backlog.md:16-19`)
через App-based токены, а не через «the one-time GitHub token used for
initial publication».

**Почему это важно:** Если токен из самого первого бутстрап-пуша до сих пор
не отозван — это реальная незакрытая экспозиция credential, самая опасная
категория для проекта, чьё ядро — «не допустить утечки секретов». Если он
уже отозван, а пункт просто забыли вычеркнуть — P0-список теряет доверие как
источник актуальных приоритетов, и будущий агент/человек либо повторит уже
сделанную работу, либо, хуже, пропустит реально открытый пункт, решив, что
весь P0-блок — это «то же самое старьё».

**Варианты:**
- A) Проверить фактический статус каждого из трёх пунктов (существует ли ещё
  этот токен; есть ли уже sentinel-leak регрессионный тест в E2E gate) и либо
  перенести выполненные в `## Completed`, либо оставить в P0 с датой
  последней проверки — плюс: список снова достоверен; минус: требует
  однократной ручной/агентской проверки внешнего состояния (GitHub token,
  E2E test suite).
- B) Оставить как есть, полагаясь на то, что «P0 без статуса = ещё не
  проверено» — плюс: ноль работы сейчас; минус: не отличить «забыли
  вычеркнуть» от «реально висит открытый токен», а именно это и есть риск.
- C) Добавить к каждому P0-пункту явную дату последней ручной проверки и
  ссылку на коммит/PR, который её подтвердил — плюс: устраняет двусмысленность
  навсегда для будущих пунктов; минус: requires process discipline going forward.

**Моя рекомендация:** A — конкретно для токена и repo-settings пунктов: это
разовая проверка, а не работа по ADR 0008 freeze (это не «release-engineering
ceremony», это уже случившийся факт, который надо либо подтвердить, либо
исправить).

**Твой ответ:** A — подтверждено 2026-07-30: см. backlog.md (два пункта закрыты в Completed с evidence, revoke-токен остаётся в P0 как требующий ручной проверки владельца).

## Вопрос 2: Bounded evidence-ledger окно (64 коммита) не имеет исключения из фриза ADR 0008

**Где:** `docs/adr/0008-freeze-release-ceremony-require-personalos-link.md:30-33`
vs `docs/release-refactor-backlog.md:454-484` (item 11) и `docs/adr/0003-compact-release-evidence-ledger.md:126-130,148-153`

**Что противоречит чему:**
ADR 0008 говорит буквально: «Stop further investment in release-engineering
ceremony (Homebrew tap polish, provenance/SBOM, **evidence-ledger
extensions**) beyond what already exists.»

Но `release-refactor-backlog.md` item 11 (`## 11. Automatic evidence-only
ledger genesis`) документирует жёсткий структурный лимит: «Both anchored and
legacy lineages have a 64-commit validation window... The observed two-commit
production baseline therefore had 62 append slots before this stage and is
expected to have 61 after the next successful patch» — и явно требует
дальнейшей работы: «**Residual architecture backlog:** design and review a
checkpoint or Merkle summary **before the validation window is exhausted**...
Neither follow-up authorizes rewriting the current branch.» Это же
подтверждается ADR 0003:148-153 как открытый пункт. `release-refactor-backlog.md:657-659`
(Suggested implementation order, шаг 3) прямо планирует эту работу: «Design
the evidence checkpoint/Merkle transition before the bounded history window
becomes operationally tight; keep legacy history immutable.»

Это ровно «evidence-ledger extension» — то есть работа, которую ADR 0008
формально замораживает — но при этом это не опциональное улучшение, а
предотвращение будущего hard-fail релизного инварианта (append rejected
before any mutation once the window is exhausted). ADR 0008 нигде не
упоминает этот лимит и не делает для него исключения.

**Почему это важно:** Каждый успешный релиз с v2-эвиденсом расходует один
слот из bounded-окна (сейчас ~61 из 64). Если фриз действует буквально и
никто не спроектирует checkpoint/Merkle до исчерпания окна, следующий релиз
после исчерпания либо провалится на append (fail-closed по дизайну ADR 0003),
либо кто-то в спешке нарушит фриз без нормального ADR-процесса. Это
единственный найденный в документах пункт, где «ничего не делать» само по
себе гарантированно ломает релизный конвейер в обозримом будущем — не «если»,
а «когда».

**Варианты:**
- A) Явное исключение в ADR 0008 (или дополнение к нему) для «structural
  necessity to keep an existing invariant alive», отдельно от «нового
  scope/ceremony» — плюс: закрывает дыру без нарушения духа фриза; минус:
  требует признать, что не любая работа над evidence-ledger — это «ceremony».
- B) Считать это уже покрытым фразой ADR 0008 «or a security requirement
  driving them» (относится к backlog.md P1/P2, но по духу применимо и здесь)
  — плюс: не нужен новый документ; минус: эта фраза формально адресована
  `backlog.md`, а не `release-refactor-backlog.md`, и не определяет, кто
  решает, что считается «security requirement» (см. Вопрос 5).
- C) Игнорировать до момента, когда окно реально почти исчерпано — плюс:
  ничего делать сейчас не нужно; минус: полагается на то, что кто-то будет
  отслеживать оставшийся счётчик слотов вручную при формально «замороженном»
  бэклоге, откуда легко выпасть из внимания.

**Моя рекомендация:** A — зафиксировать явно, что «поддержание уже
существующего инварианта живым» не является «новым scope» и не требует
PersonalOS-потребителя как обоснование, в отличие от Homebrew polish/SBOM
расширений.

**Твой ответ:** A — добавлено явное исключение в ADR 0008 (2026-07-30): checkpoint/Merkle для evidence-ledger освобождён от freeze как структурная необходимость, не ceremony.

## Вопрос 3: docs/release-refactor-backlog.md — это всё ещё «активный roadmap», не аннотированный фризом ADR 0008

**Где:** `docs/release-refactor-backlog.md:651-671` (Suggested implementation order) vs `docs/adr/0008-freeze-release-ceremony-require-personalos-link.md`

**Что противоречит чему:**
ADR 0008 (2026-07-30, самый свежий документ в репозитории) явно ограничивает
только `backlog.md` P1/P2 («Backlog P1/P2 items (see `backlog.md`) are gated
behind an explicit "does this serve PersonalOS" check»). `backlog.md:14-15,25`
действительно ссылается на ADR 0008 и явно её гейтит.

Но `docs/release-refactor-backlog.md` — отдельный, куда более детальный
бэклог из 13 пунктов с собственным «Suggested implementation order» (строки
651-671), который перечисляет как следующие шаги item 13 (artifact cleanup),
item 6 (latency investigation), item 11 (Merkle checkpoint), items 1/2/3/5/7/8/9/10
— и нигде не упоминает ADR 0008 и не помечен как замороженный. Читатель этого
файла в отрыве от `backlog.md`/ADR 0008 увидит активный, проработанный,
проранжированный план работ, а не «заморожено, пока нет PersonalOS-потребителя
или security-обоснования».

**Почему это важно:** Это прямое расхождение source-of-truth: один документ
(свежий ADR) говорит «стоп», другой (детальный бэклог, тот же день или
раньше) продолжает выглядеть как активная дорожная карта release-инженерии —
именно того рода работы, которую ADR 0008 называет «disconnected from
[PersonalOS] goal». Будущий агент, открывший только
`release-refactor-backlog.md`, с высокой вероятностью начнёт делать пункты 1,
2, 3, 5, 6 и т.д., напрямую нарушая только что принятое решение владельца —
потому что ничто в самом файле не подсказывает, что он частично заморожен.

**Варианты:**
- A) Добавить в начало `docs/release-refactor-backlog.md` явную ссылку на
  ADR 0008 и статус каждого пункта (frozen / security-exception / already
  implemented) — плюс: один источник правды, дешёво; минус: требует
  однократной разметки всех 13 пунктов.
- B) Оставить как есть, полагаясь на то, что ADR 0008 и `backlog.md` будут
  прочитаны первыми в любом будущем сеансе — плюс: ноль работы; минус:
  ADR 0008 текстуально не покрывает этот файл вообще, так что это не защита,
  а совпадение по названию каталога `docs/adr/`.
- C) Слить `docs/release-refactor-backlog.md` в `backlog.md` под одним общим
  фризом — плюс: устраняет саму возможность рассинхронизации; минус: теряется
  разделение «продуктовый бэклог» vs «инженерный релиз-рефакторинг бэклог»,
  которое, судя по объёму item 1-13, было осознанным.

**Моя рекомендация:** A — минимальное вмешательство, сохраняет оба документа
раздельными (у них разная гранулярность и аудитория), но убирает
рассинхронизацию с governance.

**Твой ответ:** A — все 13 пунктов docs/release-refactor-backlog.md размечены статусом (frozen / already implemented / exception) 2026-07-30; добавлена ссылка на ADR 0008 в заголовок файла. Item 13 дополнительно помечен как требующий отдельного внимания владельца (см. note) — возможный уже накопленный billing-риск, а не гипотетический.

## Вопрос 4: «No automatic secret rotation» (charter) vs «Secret rotation workflow helpers» (backlog P2) — граница не определена

**Где:** `docs/project-charter.md:17-21` vs `backlog.md:32`

**Что противоречит чему:**
`project-charter.md` перечисляет как «Current Non-Goals»: «No automatic
secret rotation.» Это сформулировано как постоянная архитектурная граница
(charter — самый «конституционный» документ проекта), а не как отложенный
пункт бэклога.

`backlog.md` P2 (гейтится ADR 0008, но не запрещён навсегда) содержит:
«Secret rotation workflow helpers.» README.md:291-303 («## Rotation») описывает
текущее поведение как полностью ручное: «Revoke and rotate credentials
externally, then update the stored value: `env-vault secret set
nexus-token`» — то есть сегодня «helpers» не существует и заявленное
non-goal не нарушено. Но ни один документ не определяет, где проходит
граница между «helper», который просто облегчает существующий ручной flow
(например, комбинированная команда «revoke old + prompt for new + remove
stale mapping»), и функциональностью, которая уже подпадает под «automatic
rotation» (например, scheduled/triggered ротация без участия человека).

**Почему это важно:** Без явного определения любой будущий PR с пометкой
«implements backlog P2 rotation helper» может как остаться безобидным UX-
sugar, так и незаметно пересечь границу non-goal charter — и оба варианта
формально «соответствуют» какому-то документу. Это классическая неявная
развилка: решение зависит от контекста, которого нет ни в charter, ни в
backlog.

**Варианты:**
- A) Уточнить в `project-charter.md` non-goal явной формулировкой: «No
  automatic (scheduled/triggered) secret rotation; manual-invocation helpers
  around the existing set/remove flow are in scope» — плюс: снимает
  двусмысленность раз и навсегда; минус: требует также уточнить backlog P2
  пункт тем же языком.
- B) Оставить как есть и решать вопрос ad hoc при появлении конкретного PR —
  плюс: ноль работы сейчас; минус: конкретный PR — плохое время разрешать
  архитектурный вопрос, решение будет приниматься под давлением уже
  написанного кода.
- C) Удалить «Secret rotation workflow helpers» из backlog P2 вовсе, раз
  charter уже объявляет ротацию non-goal, а README показывает, что ручной
  путь и так тривиален (`secret set` поверх существующего имени) — плюс:
  убирает саму развилку; минус: теряется место для потенциально полезной,
  но действительно неавтоматической идеи (например, «list secrets older than
  N days» без какой-либо автоматизации).

**Моя рекомендация:** A — сохраняет пункт бэклога как валидный (это
действительно может быть полезно), но привязывает обе формулировки к одному
явному критерию «требует ли это ручного вызова человеком каждый раз».

**Твой ответ:** A — project-charter.md уточнён явным критерием (ручной вызов vs автоматика), backlog.md P2 пункт получил ту же формулировку (2026-07-30).

## Вопрос 5: ADR 0008 — «or a security requirement driving them» не определено

**Где:** `docs/adr/0008-freeze-release-ceremony-require-personalos-link.md` (implicit, gating clause) vs `backlog.md:14-15,25`

**Что противоречит чему:**
`backlog.md:14-15` формулирует гейт P1 как: «none of these are picked up
without an explicit PersonalOS consumer **or a security requirement**
driving them.» Ни ADR 0008, ни `backlog.md`, ни `AGENTS.md` не определяют, что
именно квалифицируется как «security requirement» и кто это оценивает.
Пункты вроде P2 «Optional Vault/1Password/KeePassXC connectors» или P1
«Evaluate whether GoReleaser would materially improve the working custom
release and Homebrew pipeline» могут быть представлены как security-driven
(«снижает custom-код в security-критичном release path» — сама
`release-refactor-backlog.md` item 4 говорит «central transport code becomes
security critical») почти с равным основанием, что и не быть.

**Почему это важно:** Без критерия эта оговорка — единственная реальная
дыра в иначе строгом фризе ADR 0008 — может быть использована (агентом или
человеком под давлением дедлайна) для обоснования почти любого P1/P2 пункта,
сводя фриз к декоративному правилу.

**Варианты:**
- A) Явно определить в ADR 0008 (или отдельном коротком дополнении), что
  «security requirement» означает: конкретная, уже эксплуатируемая или
  документированная (например, в `SECURITY.md`/`docs/security.md`) уязвимость
  или экспозиция, а не общее «уменьшает attack surface» рассуждение — плюс:
  закрывает лазейку; минус: требует явно решить пограничные случаи заранее.
- B) Оставить как есть и требовать от владельца точечного решения по каждому
  конкретному пункту при его предложении — плюс: гибкость; минус: тот же
  риск, что и в Вопросе 4 — решение принимается в момент, когда уже есть
  мотивация протолкнуть работу.

**Моя рекомендация:** A, но с низким приоритетом относительно Вопросов 1-3 —
это скорее гигиена governance, чем активный риск прямо сейчас.

**Твой ответ:** A — ADR 0008 дополнен узким определением 'security requirement' (конкретная документированная/эксплуатируемая уязвимость, не общее hardening-рассуждение) (2026-07-30).

## Вопрос 6: AGENTS.md смешивает стабильные security-инварианты с деталями реализации, дублируя design.md/ADR

**Где:** `AGENTS.md:16-64` (Hard Security Rules) vs `docs/design.md` и `docs/adr/0002,0006`

**Что противоречит чему:** Не прямое противоречие, а отклонение от
общепринятой практики разделения слоёв документации. `AGENTS.md` — по
объявленному назначению файл агентских правил — содержит не только
стабильные инварианты («never print secret value», «no plaintext backend»),
но и версионно-специфичные детали механизма релиза: конкретные имена функций
(`release_require_typed_contract_projection`), конкретные имена скриптов
(`scripts/release/authorize-and-merge-release-pr.sh`,
`scripts/release/releasetransport.sh`), конкретные схемы файлов
(`release/contract-history.v2.json`, `release/github-transport-boundary.v1.json`).
Те же самые факты подробно и авторитетно документированы в `docs/design.md`
и ADR 0002/0006 — то есть одна и та же информация о reализации живёт в двух
местах одновременно.

**Почему это важно:** Это классическое нарушение single-source-of-truth /
DRY на уровне документации. Любое изменение имени скрипта, функции или файла
схемы в реализации требует синхронного обновления и `design.md`/ADR, и
`AGENTS.md` — а расхождение между ними не поймает ни один компилятор
(в отличие от кода). Чем детальнее `AGENTS.md`, тем выше шанс, что он
незаметно устареет относительно фактической реализации, и агент начнёт
следовать устаревшему конкретному правилу вместо актуального.

**Варианты:**
- A) Оставить в `AGENTS.md` только инварианты (что нельзя делать/что должно
  быть истиной), убрав конкретные имена функций/скриптов, заменив ссылкой
  «см. `docs/design.md` §Release Artifact Builds» — плюс: `AGENTS.md`
  становится по-настоящему стабильным слоем правил; минус: требует
  переписать существенную часть файла, риск потерять точность formulировок,
  которые сейчас служат буквальными test-oracle для агентов.
- B) Оставить как есть — эти детали, судя по стилю ADR/backlog документов,
  скорее всего написаны намеренно избыточно точно как защита от
  «creative reinterpretation» агентом — плюс: максимальная защита от неверной
  трактовки прямо сейчас; минус: продолжающийся риск рассинхронизации со
  временем, особенно теперь, когда ADR 0008 заморозил активную работу над
  release-инженерией (то есть `design.md` тоже перестанет обновляться, и оба
  документа будут дрейфовать вместе, но не обязательно синхронно).

**Моя рекомендация:** B при текущем масштабе проекта (один разработчик, один
CLI) — стоимость рефакторинга документации выше эффекта, а фриз ADR 0008
снижает скорость, с которой оба документа могут разойтись. Отметить это как
известный технический долг, не блокирующий текущую работу.

**Твой ответ:** B — оставлено как есть; текущий масштаб проекта не оправдывает рефакторинг документации, ADR 0008 и так снижает скорость дальнейшего расхождения.

## Вопрос 7: docs/design.md не описывает команду `doctor`, хотя она входит в MVP surface и задокументирована в README

**Где:** `AGENTS.md:76` vs `docs/design.md` (Architecture / Exec Flow / Output Schema, нет упоминаний) vs `README.md:232-239`

**Что противоречит чему:** `AGENTS.md` объявляет `env-vault doctor` частью
разрешённого MVP command surface. `README.md:232-239` полностью документирует
её: «`doctor` reports config path and backend status without printing secret
values», включая `--json` режим. Но `docs/design.md` — канонический
архитектурный документ проекта — ни разу не упоминает `doctor` ни в разделе
Architecture, ни в Exec Flow, ни в Output Schema, хотя команда явно
реализована (подтверждено независимо: `internal/cli/cli.go`,
`e2e/scenarios.json` содержат `doctor`).

**Почему это важно:** `design.md` — единственный документ, на который
явно ссылается сам код репозитория как источник правды об архитектуре
(например, design.md сам ссылается на `docs/e2e.md` и
`docs/e2e-baseline.json` для деталей). Отсутствие `doctor` создаёт слепое
пятно: агент, который для понимания архитектуры читает только `design.md`
(что явно предполагается его ролью «Design» документа), не узнает о
существовании и контракте этой команды, о том, какой у неё output schema
(human/JSON), обрабатывается ли она тем же error contract (`code`,
`message`, `remediation`), участвует ли в dry-run семантике и т.д.

**Варианты:**
- A) Добавить в `docs/design.md` короткий раздел `## Doctor`, аналогичный
  README, но на уровне архитектурного контракта (какие backend/config
  проверки выполняются, участвует ли в output envelope, error codes) — плюс:
  закрывает пробел один раз; минус: требует свериться с реальным поведением
  команды в коде, что выходит за рамки текущей «только документы» задачи.
- B) Оставить как есть, полагаясь на README как единственный источник
  контракта doctor — плюс: ноль работы сейчас; минус: README ориентирован на
  конечного пользователя, а не на архитектурный контракт (не описывает error
  codes/output envelope), так что этот пробел не эквивалентен переносу
  информации в другое место — она реально отсутствует на архитектурном
  уровне.

**Моя рекомендация:** A, но не срочно — это документационный долг, а не
активный риск, сравнимый с Вопросами 1-3.

**Твой ответ:** A — добавлен раздел ## Doctor в docs/design.md (2026-07-30), сверен с реальным кодом (internal/cli/cli.go: doctorCommand).

## Вопрос 8: `release/contract.v1.json` остаётся «живым» файлом верхнего уровня, хотя объявлен полностью неактуальным

**Где:** `release/contract.v1.json` (файл целиком) vs `AGENTS.md:25-30` и `docs/adr/0006-versioned-operational-release-contract.md` (Historical authority section)

**Что противоречит чему:** `AGENTS.md:25-30` и ADR 0006 явно и многократно
утверждают, что `release/contract.v1.json` в текущем расположении «is not the
archive or a source of new operational defaults», а настоящий архив — это
отдельный `release/history/contract.v1.json`. Тем не менее файл
`release/contract.v1.json` физически лежит в том же каталоге `release/`,
рядом с авторитетным `release/contract.v2.json`, с почти идентичной
структурой (то же `schema_id` семейство, те же поля `version_policy`,
`blocked_versions`, `legacy_rebuild`) — визуально неотличим от «текущего»
файла без чтения многостраничного ADR.

**Почему это важно:** Общепринятая практика для «этот файл больше не
источник правды» — физически переместить его в архивную директорию
(`release/history/`, куда уже переехал канонический v1), а не полагаться
исключительно на текстовое предупреждение в отдельном документе. Сейчас два
почти одинаковых JSON-файла с разным реальным статусом лежат рядом — это
prime target для случайного редактирования не того файла, особенно учитывая,
что ADR 0008 теперь замораживает дальнейшую release-инженерию, а значит эта
уборка, скорее всего, не случится в обозримом будущем и застрянет в
«переходном» состоянии на неопределённый срок.

**Варианты:**
- A) Переместить `release/contract.v1.json` в `release/history/` (или удалить,
  если он побайтно совпадает с уже заархивированной копией) в рамках этой же
  небольшой документационной уборки — плюс: устраняет саму возможность
  путаницы; минус: формально это уже изменение состава `release/*`, то есть
  release-related change, который по духу ADR 0008 может потребовать
  отдельного обоснования, даже будучи чисто документационным.
- B) Оставить файл на месте, но переименовать во что-то явно не похожее на
  «текущий контракт» (например, `release/contract.v1.json.frozen` или
  добавить `"_status": "inert-transition-artifact"` в сам JSON) — плюс:
  меньше риска, что это «release change»; минус: нестандартное расширение
  файла может сломать любые скрипты, которые всё ещё читают его по старому
  пути (что противоречило бы описанной в ADR 0006 роли «incident-bearing
  transition artifact for source revisions that still contain it»).
- C) Ничего не делать — риск ошибки снижается тем, что оба файла всё равно
  под версионным контролем и любое случайное использование v1 в новом коде,
  по утверждению ADR 0006, должно быть поймано strict-parity тестами — плюс:
  ноль работы; минус: полагается на тесты, которые не входят в область этого
  документного аудита и не были проверены.

**Моя рекомендация:** C на время действия фриза ADR 0008 — это чисто
стилистический риск, смягчённый (по заявлению ADR 0006) тестами на уровне
кода; не стоит тратить единственное разрешённое сейчас «security requirement
или PersonalOS consumer» обоснование на файловую гигиену.

**Твой ответ:** C — оставлено без изменений; риск смягчён тестами по ADR 0006, не тратим freeze-исключение на файловую гигиену.

## Вопрос 9: `docs/design.md` не уточняет, участвует ли `profile show` в том же lock/validation flow, что и create/add/remove

**Где:** `docs/design.md:60-63` («Config Schema» / lock section)

**Что противоречит чему:** Design.md явно говорит: «Profile create/add/remove
wrap the complete load, mutation, validation, and same-directory save in an
exclusive lock from `github.com/gofrs/flock`...» — `show` (входящий в MVP
surface по `AGENTS.md:74`) не упомянут вообще. Поскольку `show`, вероятно,
только читает конфиг (не мутирует), намеренное исключение из lock-flow может
быть корректным дизайном (read без эксклюзивной блокировки — обычная и
допустимая практика), но документ не формулирует это как решение — он просто
молчит.

**Почему это важно:** Небольшая, но реальная неявная развилка: читатель не
может отличить «show осознанно не берёт lock, потому что это чистое чтение»
от «про show просто забыли написать в этом разделе». При параллельном
`profile create/add/remove` мутации во время чтения `show` могло бы вернуть
неконсистентное (частично записанное, если не atomic-replace) состояние —
хотя atomic replace, описанный чуть выше в том же разделе, вероятно, и так
это предотвращает независимо от lock.

**Варианты:**
- A) Добавить одну строку в `docs/design.md`, явно говорящую, что `show`
  выполняет unlocked read, полагаясь на atomic config replace для
  консистентности — плюс: закрывает двусмысленность одной строкой; минус:
  требует свериться с реальным кодом, что вне рамок этой чисто документной
  задачи.
- B) Оставить как есть — минус невелик, поскольку atomic replace, судя по
  описанию, и так технически защищает от порванного чтения независимо от
  наличия lock.

**Моя рекомендация:** B — самый низкий приоритет из всех найденных вопросов,
не блокирует ничего.

**Твой ответ:** B — оставлено как есть; самый низкий приоритет, atomic replace и так защищает от несогласованного чтения.
